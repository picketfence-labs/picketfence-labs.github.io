01

Box本人権限を維持するKong経由接続は成立

Copilot StudioのURLを指定して登録したMCP接続からKong AI Gateway 2.3.1を経由し、本人のBox OAuthトークンをそのままBox MCPへ渡す接続を実証した。Entra OBOやToken Vaultは、この基本中継に必須ではない。

成立性を説明する認証・認可の分担

Copilot Studioを利用する入口の本人認証・エージェント利用許可と、CopilotからBoxを利用するOAuth・Boxコンテンツ認可は別の連携。入口でEntra IDに認証されたことだけでBox権限が付与されるわけではない。Box OAuthで本人のトークンを取得し、そのトークンをBox MCPへ渡す。

CopilotとBoxの間にKongを置く基本中継では、同じ本人Boxトークンを保持して転送する。したがってEntraトークンの追加提示やOBOによるBoxトークンへの交換は必須ではない。実際に、追加Entraなしの同じBox OAuth接続でwho_am_iが成功し、isError=falseと同時刻Gateway POST200/202を照合した。これは接続と本人照会の実証で、全ファイル権限・全tool・顧客環境を網羅した試験ではない。

提供資料で修正が必要なのは「直接接続だけが本人権限を保てる」という技術的な結論。一方、カタログの既製Box接続dialogと、任意URLを指定する標準MCPオンボーディングを区別する。後者は標準UIでURLとBox OAuthを設定でき、独自プラグインやMCPサーバーの開発は不要。資格情報・callback・接続設定の保守・Gateway運用は必要。

判断の焦点は、この負担を踏まえてもMCP横断の流量・監査観測・ツール統制を共通化する価値があるか。直結にもCopilot StudioとBoxの制御があり、Kong経由を全用途で必須とはしない。

別資料のスライドは表紙込み10枚。本文1〜4は基本接続とメリット、本文5〜6は組織ルール、本文7は実検証環境、本文8〜9はKong Identity＋Token Vault拡張案。

今回の実機検証構成：ACA・AI Gateway・Konnect

専用検証環境をMicrosoft Azure Container Apps（ACA）上に構築し、Konnect（US）からAI Gatewayを管理した。クラウド構成は宣言的に保存している。Token VaultとKong Identityはこの実測環境には追加していない。

配置と境界

スライド08の外枠はMicrosoft／Azureクラウドの論理的な配置。Entra IDとCopilot StudioはMicrosoft管理サービスであり、検証用AzureサブスクリプションやACAのVNetへ自前配置したものではない。自分たちで構築した稼働基盤はJapan EastのContainer Apps環境と、そのコンテナ上のAI Gatewayである。

通信経路・認証・管理の詳細

  1. Copilot Studioの標準MCP接続から、ACAの公開FQDNのHTTPS /box-mcpへ要求する。ACAのTLS終端からGatewayコンテナまでは内部HTTP。HTTPS入口を別のアプリケーション要素としては設けていない。
  2. 基本試験ではBox OAuthのBearer Bを受領してそのままBox MCPへ転送。Entra追加送信試験では同じAuthorization: Bearer Bにentra-access-token: Aを追加し、GatewayでAを削除してからBoxへ送る。
  3. Gatewayはhttps://mcp.box.comへHTTPSで接続。本人/グループ診断時のみ、同じBでhttps://api.box.com/2.0/users/meとmembershipsも照会した。常時の認可処理にはまだ組み込んでいない。
  4. Konnect（US）とはデータプレーン用証明書のmTLS管理接続を使用。Control Planeの設定とPolicyを反映する。CopilotからBoxへの業務データ通信をKonnect経由にする構成ではない。

この実測環境ではKong Identity／Token Vault／Entra署名検証／組織ACLは未構築。既存診断Policyのヘッダー削除順序は、将来の認証・ACL導入時に変更が必要。

07

Kong IdentityとToken Vaultで接続先資格情報を集約

公開仕様に基づくKong Identity＋Token Vaultの拡張構成案。今回のBox接続PoCには未適用・未実証。「Entra IDのみ」はクライアントがGatewayへ提示する入口の資格情報を指し、各サービスがEntra tokenをそのまま受け付けるという意味ではない。

入口Aと接続先Bを分ける

Token Vaultは信頼する企業IdPのtokenを検証し、issuer/subjectで主体を識別する。Gatewayがprovider別の登録から対応するcredentialを取得し、上流要求へ付与する。Entraが任意のSaaS tokenを発行する仕組みではない。

初回には管理者のIdP/provider設定と、利用者ごと・接続先ごとのOAuth同意・アカウント連携が必要。未連携なら登録導線へ進む。登録後も、各サービスの権限・scope・失効条件は残る。Gatewayは入口の認証とツール利用ルールを別途構成する。

Token Vaultの主体識別・provider・credential enrollment。

観点エンハンスメント1：組織ルール追加エンハンスメント2：資格情報連携
クライアントからの提示Box Bと追加のEntra AGateway入口のEntra A
Box用資格情報の利用Copilotの本人Box接続から受け取り保持GatewayがToken Vaultのprovider別登録から取得・付与
主な狙いBox権限にEntra組織基準のMCP利用制御を追加接続先/クライアントが増えても資格情報の連携・管理を共通化
前提追加header・検証済みgroup等・ACL設定Konnect TV有効化・trusted IdP・本人紐付け・provider/OAuth連携
今回の状態送信と分離転送は実証、署名/組織ACLは未実証構成案。Copilotとの登録誘導・Box TV連携も未実証

二つの拡張は併用できる。Token Vaultは資格情報の連携を担い、MCPツールの認可はGateway、データの認可は各サービスが担う。Gatewayを通るクライアントに接続先credentialを持たせる範囲を減らすという価値がある。

接続先と導入条件

  • GitHub/Slackは公開provider templateの例。Boxはcustom-oauth候補であり、Box固有の正式適合・callback/scope/refresh・Copilotでの初回認可と完了反映は別途確認。
  • Konnect Token Vaultを利用する構成。完全on-premで単独稼働する保管庫とはしない。対象org/region/製品版・有効化条件を採用時に確認。
  • 必要な利用者だけに資格情報が対応すること、複数利用者の分離、同意取消し・失効・更新失敗と運用責任を実証する。今回の検証で構築・資格情報保存は追加していない。

AI MCP ServerのToken Vault upstream連携。拡張図のGitHub/Slack/Boxは説明用の接続先で、顧客環境の導入済み構成ではない。

Kong Identityは必須。Entra利用者はいつ登録されるか

Token VaultはKonnectのKong Identity Directoryを境界として使う。Directoryのvault_enabledを有効化し、vault keyを登録する。Entra IDをtrusted IdPとして設定し、vault_access_enabled=trueでToken Vaultへのアクセスを許可する。

条件を満たせば初回利用時に自動登録される。trusted IdPのjit_provisioning_enabled=true（既定値）で、受信トークンのissuer（iss）とsubject（sub）に一致するPrincipalがない場合、Kong IdentityがPrincipalを自動作成し、本人用資格情報を紐付ける。既存の一致するPrincipalは再利用する。JITを無効にする場合は事前登録・対応付けを設計する。

Entra IDに登録済みの全ユーザーを自動で一括同期する意味ではない。Entraのgroup所属が自動同期されるとも、このJIT仕様だけからは言えない。Token Vaultは公開鍵を取得してトークンを検証する方式で、利用者情報を企業IdPへ直接照会しない。

Principalの自動作成と、Box等の接続先に対する本人OAuth同意は別。未連携の接続先には初回enrollmentが必要。Kong Identity／TV／JIT／Box固有連携は今回未構築・未実証。

5–6：Kong Identity ↔ Entra設定したissuerのdiscovery/JWKSから公開署名鍵を取得し、署名・issuer・exp/nbfを確認する。既に鍵を保持している場合は毎要求ごとに取得しない。利用者のパスワード・ユーザープロフィール・グループをEntraへ問い合わせる処理ではない。
6–7の間：Principalと資格情報の解決検証したiss/subでDirectory内のPrincipalを特定。JIT有効で一致するPrincipalがなければ作成する。本人×providerの登録済みcredentialをToken Vaultから解決する。Gateway側の認可ルールや想定audience/scopeの検証も採用構成に合わせて設定する。
7–10：Box用Bで実行登録済みのBox用資格情報BをGatewayで上流要求に付与。Entra AをBox MCPへ渡さず、BoxはBoxの本人権限で認可する。Entra tokenから任意のSaaS tokenを直接生成する仕組みではない。

Box用資格情報が未登録の場合：初回のOAuth連携

  1. 資格情報の要求に対し、enrollment URLが返る。Gatewayは呼出し元へ初回認可の導線を提示する。
  2. 利用者がブラウザーで導線を開き、Box等の接続先で本人認証と要求scopeへの同意を行う。
  3. 接続先が設定済みのcallbackへ認可コードを返す。Kong Identity／Token Vaultの連携処理が、接続先との間でコードとaccess/refresh tokenを交換し、本人×providerに対応するcredentialを保存する。Gatewayのcallback公開を含む実際の経路とBox側の設定は検証時に照合する。
  4. 登録後の呼出しから、図07-1の7以降へ進める。Copilot Studioでの認可URL提示・完了検知・再試行、Box custom-oauthのcallback/scope/refresh適合は今回未検証。

PrincipalのJIT登録と、Boxアカウントへの本人同意は別の処理。JITだけではBox用資格情報は作られず、Entraの全ユーザーやSecurity Groupの一括同期も意味しない。

一次資料：Token Vault：trusted IdP・JIT・credential enrollment、Directory/provider/vault keyの構成手順、MCP upstreamのToken Vault利用・キャッシュ（2026/11/15確認）。Box固有連携とCopilotの初回導線は構成案であり、今回の実機結果には含めない。

OpenAPI定義は、どの設定に必要か

標準MCPオンボーディングで基本接続を作る場合、利用者がOpenAPIを手書き・インポートすることは必須ではない。Server URLとOAuth等を標準画面へ入力して登録できる。Power PlatformはそのMCP接続をコネクタとして管理する。

付録D-1/D-2は、その接続先・認証・追加パラメータを保持するOpenAPI（Swagger 2.0）の保存定義。今回はHost/Base URLの中継先指定と、Entra追加ヘッダーentra-access-tokenの入力項目を確認・再現する根拠になる。Power Appsからコネクタを手動作成する経路ではOpenAPIをインポートする。既存MCPの接続定義や追加パラメータを編集する場合はPower Apps/Power AutomateのCustom connectorsを使用できる。

OpenAPIだけでEntraの実トークンが設定されるわけではない。D-2のheader入力定義に加え、D-3のTaskDialogでSystem.User.AccessTokenを割り当てる。Box OAuthのClient ID/Secret・callback設定と本人同意も別途必要。
