01

結論

両クライアントの購読ログインを維持しながら、AI Gateway を経由した推論を Cost Management の同じリクエスト ID で照合できた。認証、タグ、上流レスポンスからの使用量抽出の3つが揃うと、誰の利用か、何の作業か、どの処理でトークンを使ったかを追える。

Codex Pro

ChatGPT ログインと別の Gateway Auth0 Cookie を併用。DP 2.3.2 の計測経路は、OpenAI 形式の AI Model と SSE 中継の組み合わせで応答・計測を実証した。

Claude Code Enterprise

Enterprise ログインと別の Gateway キーを併用した。Anthropic Messages の AI Model で応答・計測を実証し、SSE 中継は不要だった。Gateway OAuth は隔離 CP の Keycloak 構成で確認済み。運用先の企業 IdP を使う場合は、別途トークン発行と更新の条件を確認する。

実証の受入は、推論の完了・同じ ID の利用イベント・トークン数の一致。Cost Management の USD は AI Model の API 単価換算で、購読契約の請求額・残枠は各ベンダーの管理画面で確認する。実測記録

03.1

今回の暫定対応と製品側の対応状況

目的は、Codex Pro と Claude Enterprise の既存購読を維持しながら、応答の完了と Cost Management への利用イベントの到達を両立させること。採用した暫定対応と、外せる条件を以下に示す。

導入した対策と解消条件
暫定対応目的必要になった理由外せる条件
Codex Pro の SSE 中継ChatGPT Pro で推論を完了させ、DP で利用量を読み取る。DP 2.3.2 の OpenAI 形式 AI Model を直接つないだ試験では、上流応答の Content-Type が欠けた場合に SSE 正規化が失敗した。中継が成功 SSE の型を補い、完全な終端フレームと EOF を分けて DP に渡す。中継の追加後、応答と同一 ID のイベントを確認した。比較実測同じ購読・AI Model で直接接続し、応答とツール後続、同一 ID のイベント、入力・出力・キャッシュの一致を確認できた時点。構成・版が変わる場合は再検証する。
Claude Enterprise の Gateway キー企業 IdP 用のアプリ登録が済むまで、既存の Enterprise ログインと Cost Management 計測を継続する。企業 IdP で対象 Gateway 用の OAuth クライアント登録が必要だったため、DP は別ヘッダーのキーで認証した。Messages の計測は Consumer 帰属で成立した。IdP 管理者から承認済みアプリの発行・更新条件を受領し、試験ルートで購読 Bearer と Gateway OAuth を分けて送信できること、本人帰属、トークン更新、Enterprise 管理設定を確認する。
ローカル HTTPS 用の CA 調整クライアントが TLS を検証した状態でローカル DP に到達できるようにする。旧 CA の IP 名前制約を Claude Code の Bun が受け付けなかった。ローカル CA と DNS／IP の SAN を更新し、Claude Code は localhost を使う。TLS の拒否段階ではモデル要求が DP に届かない。クライアントが標準で信頼する CA と DNS 名で Gateway を提供する構成。これは今回の端末の証明書運用で、Konnect のテレメトリー接続用 mTLS は別に管理する。

公開リリースで確認する項目

  • Codex Pro は、中継なしで Responses のストリーミング、ツール実行後の応答、同じリクエスト ID の利用イベント、トークン内訳を確認する。今回の結果は DP 2.3.2 の検証構成に限る。
  • Claude Code は、購読用と Gateway 用の資格情報を分けて扱えること、企業 IdP の更新と本人帰属、必要な Enterprise 管理設定が動作することを確認する。

クライアント設定の詳細

Codex CLI · ChatGPT ログイン＋別の Gateway OAuth

ユーザー側の ~/.codex/config.toml でプロバイダーを定義し、明示的に選択する。今回、同じプロバイダーを選ぶ gateway-profile プロファイルを利用した。リポジトリ側の .codex/config.toml で同じ接続設定が適用されるとは想定しない。

model = "YOUR_CODEX_MODEL"
model_provider = "example-gateway"

[model_providers.example-gateway]
name = "Local AI Gateway"
base_url = "https://gateway.example.com/codex"
wire_api = "responses"
requires_openai_auth = true
supports_websockets = false

[model_providers.example-gateway.gateway_oauth]
authorization_url = "https://idp.example.com/authorize?audience=YOUR_API_IDENTIFIER"
token_url = "https://idp.example.com/oauth/token"
client_id = "PUBLIC_NATIVE_CLIENT_ID"
redirect_port = 43127
scopes = ["openid", "offline_access", "invoke:codex"]
delivery = { kind = "cookie", name = "codex_gateway_oauth" }

[model_providers.example-gateway.http_headers]
"ai-cost-project" = "gateway-validation"
"ai-cost-agent-surface" = "cli"

[model_providers.example-gateway.env_http_headers]
"ai-cost-workflow-run" = "AI_COST_WORKFLOW_RUN"
"ai-cost-scm-repository" = "AI_COST_SCM_REPOSITORY"
"ai-cost-scm-issue" = "AI_COST_SCM_ISSUE"
  • 値は説明用。公開クライアントに Authorization Code＋PKCE を許可し、例では http://127.0.0.1:43127/callback を登録する。今回の Auth0 では認可 URL の audience を指定した。IdP に応じて issuer・audience・scope、必要な resource と更新時の条件を照合する。
  • requires_openai_auth = true が既存の ChatGPT 認証を使う設定。DP は codex_gateway_oauth を検証・除去し、Authorization と、ある場合の ChatGPT-Account-ID を購読上流に渡す。この DP で試験した別ヘッダー方式には Bearer 形式の互換差があったため Cookie を採用した。
  • 購読維持のキー方式では base_url をキー認証ルートに切り替え、env_http_headers に "X-Local-Gateway-Key" = "GATEWAY_KEY" を追加する。キー用プロバイダーでは OAuth テーブルを使わず、requires_openai_auth = true を維持する。専用 CA を使うローカル HTTPS では CODEX_CA_CERTIFICATE を起動プロセスに渡す。
  • Orca から起動する場合は、対象 Worktree の Codex Command にランチャーを設定する。実効プロバイダー、CA、project／agent-surface と指定済みの Run・Issue を選ぶ。新規 Chat で接続先とタグの反映を確認する。

OpenAI Gateway OAuth と資格情報 · Responses 互換性 · 接続検証の条件

Claude Code · Enterprise ログイン＋別の Gateway 資格情報

既存の Claude ログインを保ち、Gateway URL、公開 CA、追加ヘッダーを対象起動で配布する。下の例は Bash での暫定キー方式。キーは既に承認された秘密管理からプロセスへ供給する。

export ANTHROPIC_BASE_URL='https://gateway.example.com/claude'
export NODE_EXTRA_CA_CERTS='/absolute/path/gateway-ca.crt'
export CLAUDE_CODE_GATEWAY_HINT_HEADERS=1

ANTHROPIC_CUSTOM_HEADERS="$(printf '%s\n' \
  "X-Local-Gateway-Key: ${GATEWAY_KEY}" \
  "ai-cost-project: gateway-validation" \
  "ai-cost-agent-surface: cli" \
  "ai-cost-workflow-run: ${AI_COST_WORKFLOW_RUN}" \
  "ai-cost-scm-repository: ${AI_COST_SCM_REPOSITORY}" \
  "ai-cost-scm-issue: ${AI_COST_SCM_ISSUE}")"
export ANTHROPIC_CUSTOM_HEADERS
claude --model YOUR_CLAUDE_MODEL
  • DP は X-Local-Gateway-Key を検証し、既存の Authorization、anthropic-version、anthropic-beta を Anthropic へ渡す。Messages で使用量を照合し、/v1/messages/count_tokens は転送・機能確認に使う。
  • Gateway OAuth を使う場合はキー行を x-kong-id-token: <対象 Gateway 用アクセストークン> に替える。Gateway で issuer・audience・scope・署名を検証し、受け取った資格情報を上流送信前に除去する。更新は組織の認証フローとクライアント側の更新経路で担う。複数の Gateway を運用する場合は、接続先ごとに必要な audience を確認する。
  • apiKeyHelper は組織の Gateway を主認証にする公式機能。公式仕様ではヘルパーの資格情報が Authorization と x-api-key に入る。購読 Bearer を維持する2資格情報の経路は、別ヘッダーを使う。ANTHROPIC_AUTH_TOKEN や API キーを使う設定に切り替える際は、どの契約で課金されるかを照合する。
  • 設定先はシェル、~/.claude/settings.json の env、管理設定、対象起動の --settings。Orca ランチャーは Orca の --settings と Gateway URL を統合して渡す。企業運用で管理設定が適用されるかは対象の /status の Setting sources と実機で確認する。

Claude Code の公式接続設定 · ヘッダーの契約 · 接続検証の条件

接続検証のチェックリスト
  1. 対象の CLI・新規 Chat を開き、実効 URL、モデル、TLS 信頼、Gateway 認証と購読ログインの両方を確認する。ローカル DP の証明書名はクライアントが使う localhost または 127.0.0.1 と一致させる。
  2. Codex は /models、Responses の SSE 終端とツール後続、Claude Code は /v1/messages の終端と /v1/messages/count_tokens の応答を確認する。必要な管理機能は個別に確認する。
  3. 小さな合成要求の Gateway リクエスト ID を取る。同じ組織・リージョン・時刻で Cost Management のイベントと CLI のトークンを照合し、Run・Issue・role と本人帰属を確認する。認証不成立・TLS 失敗・応答完了後の計測欠測を別々に扱う。

中継なしの HTTP AI AgentHTTP 200、Codex のターン完了。タグを外した Events API 再照会でも同じ要求 ID は0件。DP での使用量抽出と送信の成否は未確認。
中継なしの OpenAI 形式 AI Model／透過 AI ModelOpenAI 形式の先行試験は SSE 正規化例外。別の透過試験ではターン完了。DP 2.3.2 は上流の Content-Type を見て SSE フレームを解析。型欠落時は正規化で失敗する。透過構成では、応答が完了した試験でも使用量が取得されなかった。
SSE 中継付きの OpenAI 形式 AI ModelHTTP 200、SSE と Codex のターン完了。同じ ID のイベントと合計18,883トークンを確認した対照試験あり。中継は必須の応答メディア型を補い、完全な終端フレームの直後に EOF を返す。利用量の抽出・送信は DP が担当。

クライアントが追加できるのは送信する要求ヘッダー。今回問題になったのは上流から DP へ返る SSE。DP が解析した後のレスポンスヘッダー変更だけでは、DP が解析に使う上流ヘッダーを補えない。中継が担当するヘッダーと EOF は別の条件で、両方の寄与を同じ AI Model で揃えて比較する必要がある。
