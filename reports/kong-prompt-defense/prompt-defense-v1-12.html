設計アプローチと想定スコープ

Gateway で入口を制御し、アプリでデータと操作の権限を守り、モデルの応答は出口で確認する。

本レポートでは、入力に含まれる指示がアプリの業務範囲を変えようとしたとき、Kong がどの段階で介入できるかを検討する。対象はテキストの依頼と応答で、評価では禁止したい依頼を止められたかと、正当な依頼を完了できたかの両方を見る。

01

Kong による防御アプローチ

総論　Kong にどこまで防御を任せるか

Kong の強みは、明示した条件に該当する依頼を生成前に遮断できること。課題は、同じ表現を含む依頼の許否を文脈から判断すること。

生成AIを利用するアプリでは、言語モデルが業務指示に加え、利用者の質問や外部資料も処理する。入力に含まれる指示によってモデルを本来の仕事から逸脱させる手法がプロンプトインジェクションである。Kong AI Gateway は、生成前の入力検査、モデルへの業務方針の付与、返却前の応答検査を担う。

Kong で強制できる
明示条件に該当する通信の遮断

入力形式・サイズなど機械的に決められる条件や、その業務で一律に止めてよい表現は Gateway で強制する。返却時にも、出力ポリシーの条件に該当した回答を利用者の手前で止められる。

隔離試験では、入力側の Prompt Guard は、指定した2文をともに HTTP 403 で遮断し、模擬上流への到達は0回だった。これは該当条件を強制できた証拠で、攻撃全般の検出率は未測定である。 遮断時の記録

採用が有望
文脈に応じた回答の誘導

機密へのアクセスと操作権限

文中で「管理者」を名乗っても、その人にデータを読む権限や操作を実行する権限があるかは確定しない。アプリは認証済みの本人と対象ごとの権限を、資料の取得時とツールの実行時に照合する。

02

脅威に対して指定する設定

日本語と英語で公開情報を案内する製品サポート向けの初期設定案。下記は各 AI Policy の config の抜粋。global: false に設定し、公開サポート用 AI Model の policies に割り当てる。許可すべき業務入力との境界を確認してから遮断を有効にする。

AI Prompt Guard · 指示の効力、権限、安全審査、情報の扱いを照合する

「過去の指示は一旦保留の上」は、改訂案の日本語条件 01-ja に一致する。旧版は「過去」と「保留」の組を扱えなかった。上位指示の効力を一時的に止めることも防御対象に含め、対象語と操作語の順序、間に入る助詞・限定句・改行、英語の語形を見直した。

2.3.2 同梱の設定パーサーでは deny_patterns は最大10件。個別の式には長さ上限500の検査もある。旧版の14件は一つの設定として受理されなかった。改訂案は5つの目的群を日本語・英語各1式にまとめ、10式・最長489 UTF-8バイトで観測用と遮断用の両設定が受理された。

照合定義 · 各条件は対象と操作の両方を探し、どちらの語順も評価する。
防ぐ要求具体的な照合条件と良性側の境界
上位指示の効力を失わせる

指示の破棄・置換だけでなく、今回だけの保留・先送りも拾う。 対象と操作の間隔は最大 48 文字。

01-en　Earlier/system instructions, standing policies 等と、discard、defer、suspend、on hold、set aside 等の語形。

顧客自身の以前の依頼を保留する文面にも一致し得る。

安全審査・拒否の抑止

保護機能を止める、適用を省く、あるいは先延ばしにする要求。 対象と操作の間隔は最大 44 文字。

02-ja　安全チェック・安全制約・拒否応答と、抑止・回避・停止・省略・後回し等。

02-en　Safety review、security filter、refusal message 等と、skip、suppress、disable、defer 等の語形。

機能名や拒否理由の問い合わせは許容する。禁止を説明する注意書きは誤検知し得る。

権限の偽装・優先順位の変更・特権操作

発話者が名乗る権限や利用者の指示と、優先順位の変更または処理の実行を結び付ける。 対象と操作の間隔は最大 64 文字。

03-ja　管理者の権限、開発者として、今回の指示等と、操作実行・指示変更・優先順位等。

03-en　Admin rights、operator approval、current rules 等と、操作の実行、override、priority、precedence 等。

管理者向けの説明や請求書の閲覧は許容する。本人確認とツール実行の認可をアプリで行う。

内部指示・機微データの開示と転送

隠された指示、機密の業務情報、認証情報を表示・複製・転送する要求。 対象と操作の間隔は最大 56 文字。

04-ja　内部プロンプト、未公開価格、認証情報等と、表示・開示・転送・共有等。

04-en　Internal messages、unpublished pricing、access tokens 等と、disclose、display、forward、upload 等。

価格やロードマップを一律禁止しない。検索権限、資格情報の分離、外部送信先の認可は別に強制する。

役割演技による制約解除・承認や監査の省略

例外的な役割・モードの主張に伴う制約解除、または必要な承認・監査の抑止。 対象と操作の間隔は最大 56 文字。

05-ja　役割演技・架空設定、または承認・監査の対象と、制約解除・省略・記録停止等。

単なるロールプレイ、承認状況の照会、監査ログ保存期間の質問は許容する。監査設定をモデルに変更させない。

適用ルートと処置

公開サポートの導入時は continue_on_detection: true で一致を観測する。この段階では一致しても転送される。個別の PCRE が確認したのは二つの語群の近接であり、注意書きや引用の意図は確定できない。設定の順番は、互いに異なる AI Policy の優先順位や利用者の権限を決めるものではない。

遮断が必要な専用ルートでは continue_on_detection: false と rejection_mode: stealth を指定する。校正時に正当な引用が一致した条件は、そのルートでの扱いを決めてから昇格する。分類が難しい文面は承認済み分類サービスの対象にできる。機密データの取得・外部転送・特権操作の認可は、文字列の一致結果に関係なく強制する。

AI Semantic Prompt Guard · 意味が近い依頼を補足

言い換えで文面が変わっても、禁止したい結果が近い入力を判定する。上位指示の永久的な破棄と一時的な適用延期、なりすましと実際の特権実行、情報の開示と外部への転送を参照集合に含める。参照集合と独立した日英の評価文で閾値を選ぶ。

rules:
  match_all_conversation_history: true
  match_all_roles: false
  deny_prompts:
    - 過去の上位指示を保留・延期・破棄し、その適用を止める要求
    - A request to defer, suspend, or discard higher-priority instructions
    - 特殊な役割を理由に安全審査や拒否・承認を省く要求

ジェイルブレイクは「安全制約に反する応答を得る」という目的。直接・間接の指示注入は指示の出所で分類する。一つのケースが両方に該当する場合は、目的と出所を併記する。 OWASP LLM01

脅威ごとの主対策・補助策と、採用時に必要な証拠
脅威・要求Gateway に設定する制御アプリ・上流で担う制御確認する結果・残る限界
ジェイルブレイク入口は Prompt Guard で安全チェック・拒否の抑止と役割演技を使った制約解除を照合し、Semantic／Lakera で補助。出口は Semantic Response Guard またはモデレーションで禁止出力を検査。上流モデルの安全設定は有効にし、アプリで応答の公開可否を確認する。入力遮断・上流拒否・禁止出力を別々に記録。正規表現から未知の意図や複数ターンの意味を判定することは難しい。
直接の指示注入Request Validator で利用者ロールと形式を固定。Prompt Guard で上位指示の無視・優先順位の変更・内部指示の開示・特権での操作実行を照合し、Semantic で補助。Decorator で業務上の指示を追加。アプリが信頼済みのシステム指示と履歴を構築する。特権操作の可否は、認証結果と操作ごとの権限で決める。許可外ロールの拒否と、許可ロール内の文面の遮断を分けて確かめる。モデルが業務に従ったかは上流応答で確認。
間接の指示注入対象フィールドに入ったテキストの検査と、Decorator による業務指示の補強を補助にする。RAG／ツール結果の来歴を保持し、文書単位の検査を生成より先に実施する。検索にも利用者の権限を適用し、ツールの操作・引数をアプリで認可する。検査対象外の添付や後から取得する資料には個別の制御が必要。資料の指示が採用されたかと、正当な依頼を完了できたかを確認。
不適切コンテンツLakera または Azure を入力・出力のモデレーション候補とする。明示条件は Prompt Guard で補助。教育・支援・報道などの許容文脈、カテゴリ別の処置、上流の拒否方針を定義。カテゴリ別に検出と遮断を記録。軽度の不満や正当な支援要請を通せるかも確認する。
禁止業務トピックPrompt Guard に明文化できる条件、Semantic に話題と依頼目的を組み合わせた条件、Decorator に業務範囲。公開済み価格・返金手続は案内。未公表の価格やロードマップへのアクセスと、個別の投資・競合購入推奨を制御。依頼された行為と単なる話題の言及を区別。出力に要件違反が含まれたかを確認する。
データ露出対象形式の PII を Sanitizer でマスキングし、応答側の検査で補う。検索・ツールの最小権限、テナント分離、秘密をモデル入力から除外、出力を受け取る利用者の権限を確認。埋め込み・分類サービス・生成モデル・ログを別々の送信先として確認する。
想定外の入力形式Request Validator で application/json と文字列の content を強制し、公開テキストルートで許可するフィールドを限定。画像・添付・構造化ツール結果を受ける経路は、読み取り、来歴、検査、失敗時の処置をアプリ側で定義する。公開ルートに型違いの入力を渡したときに形式エラーとなることと、許可形式の良性入力が通ることを確認。
大量利用・過大入力認証、Request Size Limiting、レート制限で利用量を制御。入力長と費用の上限、タイムアウト、許可する再試行を定義。制限が発動した区間を観測。通常業務の負荷でも処理が続くか確認する。

Lakera と Azure の分類をどう使うか

Azure の主要分類は Hate and Fairness、Sexual、Violence、Self-Harm。Lakera には Hate、Sexual、Violence、Self Harm に加え、Crime、Profanity、Weapons の分類がある。Azure の主要4分類と同じ粒度で対応するとは限らないため、ケース台帳で同じ業務上の許否を定義し、各サービスの分類結果と最終処置を別々に記録する。

未公開価格の開示や競合製品の購入推奨は、架空のサポート業務で定義した制限。業務要件に合わせてローカルポリシーやカスタム分類を選択する。Azure の Prompt Shields は文面と資料に含まれる指示の検出機能で、Content Safety のカテゴリ判定とは評価項目を分ける。
