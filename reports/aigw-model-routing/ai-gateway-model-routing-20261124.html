要点クライアントと経路キー管理適用と検証出典
01

なぜAgentsに表示されたか

最初の実装では、既存のChat Completions APIを固定URLに転送するHTTP型AI Agentを8件作成した。ルートごとにモデルと費用配賦用ヘッダーを固定し、上流APIキーはクライアントが送った。Konnectは設定されたエンティティの種類に従ってAgentsへ表示する。

現行の通信Chat Completionsクライアント → HTTPSのHTTP Agent → 固定上流。合成入力1件でHTTP 200と使用量を確認済み。
移行する通信Chat Completionsクライアント → HTTPSのAI Model → AI Model Provider → 固定上流。Providerが保管済みのキーを付与する。Flash-Liteはこの経路でHTTP 200を確認し、Modelsへの登録も読み戻した。

03

上流キーの保管と宣言

項目構成宣言範囲と運用
Config StoreConfig Store → AI Vault → AI Model Providerの上流ヘッダーStore、Secretの名前と入力参照、Vault、Provider、Model、Policyをkongctlで定義可能。キー値は実行時に安全な保管先から注入する。
Identity Token VaultDirectory → Vaultの公開鍵 → 共有 static_secret Provider → 対応するMCP ServerProvider・共有資格情報・公開鍵の宣言リソースがある。対になる秘密鍵の安全な生成・配布と上流キーの発行・失効は運用工程。HTTP Agent・AI Modelへ同じ方法で注入する対応は公式仕様で確認できなかった。
クライアント認証Gateway Consumerの入口キー上流キーと異なる権限・有効期限を持つ。クライアントは入口キーだけを使い、Providerが上流APIキーを注入する。

書込専用の秘密値は読戻しやdumpで比較できない。変更の検証には、秘密を出力せずに実行時の解決と上流への伝達を確認する。

04

移行と検証

全8件をAI Modelとして追加し、共通ProviderとConfig Storeの参照、DP同期、再planの差分0件を確認した。8経路すべてで入口キーなしの要求は401。Flash-Liteは入口キーだけを送信した合成リクエスト1回でHTTP 200、入力5・出力2トークンを確認した。他7件は登録・同期・未認証拒否まで。照会したCost ManagementイベントにFlash-Liteと同じリクエストIDは見つからなかった。

パイロットの状態と受入条件
  1. Flash-Lite 1件を別パスのAI Modelとして構成し、既存HTTP Agentへの変更・削除がないことをplanで確認する。
  2. AI Model、Provider、Vaultの保存値とDP同期を読み戻す。無効な入口キー、許可外モデル、余分なパスの要求が上流に届かないことを確認する。
  3. 推論の応答、必要なストリーム終端、使用量を確認する。Cost Managementの利用イベントと、上流側の費用計上は別々に照合する。
  4. 代表経路の疎通後に残り7件を登録した。呼び出し側は検証済みの用途から新しいURLへ移行できる。切り戻し用に既存HTTP AgentのURLを保持する。
05
