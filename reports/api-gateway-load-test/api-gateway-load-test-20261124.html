API Gateway負荷テストの方法

PoC・性能回帰・容量計画で使うツールと、実トラフィックを再現する試験設計

01

新規案件はk6を起点にする

新規のHTTP API Gateway案件では、k6で到着率を制御する容量試験と、利用者・セッションを固定する試験を両方用意する。設定の再現性を確保しやすく、Kong Gatewayの公開ベンチマークで使われている。PythonシナリオやLocust資産が既にある案件では、その資産を活かして同じ評価軸を揃える。

容量・CI回帰k6。一定の到着率でp95／p99、達成率、エラー、負荷生成機の余力を測る。
ログイン・認証更新・業務操作既存Python資産があればLocust。利用者ごとのCookieや認証情報、待ち時間、操作順序をモデル化する。新規ならk6のVUでも始められる。
接続の上限を切り分けるHTTP/2の接続数と同時ストリーム数はh2load、最小HTTPプロキシの上限はwrk／wrk2。WebSocketの保持とメッセージはk6で別ケースにする。

03

RPS、接続、利用者IDを別々に設定する

同じ1,000 RPSでも、既存の接続を使う場合と毎回TCP/TLSを張る場合では、LBとGatewayが消費するCPU・ソケット・メモリが変わる。利用者IDを増やすと、認証キャッシュやレート制限のキーの数も変わる。Gatewayがアプリケーションのセッション状態を保持するかは、認証・プラグイン・上流の設計による。

負荷の軸実トラフィックから集める値試験への反映と確認
リクエスト量平常・ピーク・バーストのRPS、ルート別比率、リクエスト／応答サイズ、クライアントの再試行容量試験は固定到着率。k6のarrival-rateは反復／秒なので、厳密なRPS制御は1反復1リクエストか実送信数で校正。応答を待つ実際の業務操作には固定VUを使い、処理遅延でRPSが低下する挙動も計測。
物理接続と同時処理同時TCP接続、接続開始/秒、keep-alive・idle時間、TLS終端とセッション再開率、HTTP/1.1・HTTP/2比率通常の再利用、接続更新の混在、接続再利用なしの比較を同じ経路で実施。TLSのフルハンドシェイクと再開を区別。HTTP/2では複数ストリームが1接続を共有するため、LBの前後とGateway→上流の接続数を実測する。
認証主体と論理セッション同時アクティブ主体、ユニークID、トークンTTLと更新、Cookie、URLやテナントの偏りテスト用アカウントをworker間で重複なく配布し、利用者ごとにログイン／JWT／Cookieを保持。ホット・コールドなID、共有資格情報を使うM2M、個別quotaを持つ利用者を案分。JWT検証だけの経路と、外部照会・更新が起きる経路を個別計測。
長時間接続とストリームWebSocket／SSE／gRPCの同時数、継続時間、メッセージ頻度・サイズ、再接続率同時接続数、確立速度、継続時間、メッセージ量、再接続を個別に制御。SSEは最初のイベント、gRPCはステータスとストリーム完了を採点。HTTPのTTFBだけでは最初の有効イベント時刻を取得できない。

容量設計の計算例

定常1,000 RPS × 平均50 ms ≈ 平均50件が処理中。毎秒20本が新規確立し平均60秒維持する条件では、約1,200本が同時接続。別々の仮定で求めた概算で、入力は観測値に置き換える。

負荷が成立したかを見る

k6では開始・完了反復と dropped_iterations を確認する。予定到着率に届いていない区間は容量合格に使わない。目標負荷を出せずに終了した時は、VUの占有、生成機の飽和、対象の遅延を照合する。

k6でログインから操作までを1反復にまとめると、反復中のCookieを保持できる。複数反復にまたがるセッションでは、シナリオに応じて noCookiesReset を設定し、再ログインや更新時の挙動を確認する。

ユースケース別に採用する試験

下表の数値は最初の試行を組むための例。試験対象の上限や推奨スペックは、実トラフィックと事前校正で決める。

ケース推奨と実施条件確認する結果
小規模PoC・CI回帰k6＋専用テスト環境。例として50→100→300 RPS、各段階5〜10分、前後版で同じルート、ペイロード、認証。既存Locust／JMeterでも規定の負荷と判定を満たせば継続。実到着率、成功率、p95／p99の差、再現性。共有CIランナーではスモークを行い、比較値は専用ジェネレーターで採る。
ピーク容量・プラグイン比較k6固定到着率。観測ピークの0.5×、1×、1.2×から校正。Gateway単体応答→模擬上流へのプロキシ→本番相当プラグイン→実上流の順。10,000 RPS級は同一リージョンの専用VM／専用ノードから始め、必要量に応じて分散。SLOを満たす持続RPSと最初の飽和点。ルート・Consumer数、ログ・トレース、外部ストアを加えた時の差を測る。
独立した認証セッションLocustまたはk6の固定VU。例として500、2,000アクティブ主体を段階投入。アカウント別のログインと更新、think time、Cookie保持、テナント間の偏りを設定。認証・更新の遅延と失敗率、キャッシュヒット、IdP／Redisの負担、想定どおりの主体別429と他主体への波及。
接続増・再接続・TLSk6で通常再利用／更新混在／HTTP接続再利用なしを比較。HTTP/2はh2loadで接続と同時ストリームを独立に振る。入口TLS終端の位置と再開率を合わせる。active／new connections、TCP/TLS時間、接続エラー、DPごとの偏り、FD・メモリ。接続再利用なしのk6オプションは再利用の制御であり、TLS再開の状態は別途観測する。
WebSocket／SSE／gRPCWebSocketはk6。SSEはイベントを読み取るクライアント、gRPCは必要な方向のストリームをサポートする版を固定。例として1,000接続を段階確立し30分維持、本番相当の時間・頻度で再試験。接続確立率、TTFTまたは最初のイベント、イベント遅延・欠落、異常切断と回復時間、LB idle timeout・drainの影響。
長時間運転・変更・障害復旧k6または既存のLocustで、通常負荷と設定変更、ローリング再起動、スケールイベントを分けて試す。数時間のsoakはデプロイ・TTLなど実イベントの周期を覆う長さを選ぶ。p99スパイクと回復時間、エラー予算、メモリ・FD・キューの増加、再接続と負荷の偏り。固定レプリカの容量試験に続けて自動スケールを測る。
06

試験環境の構成と合否判定

目的ごとに経路を決める

開発・CIではローカルまたはCIで起動確認し、性能比較は専用stagingで行う。容量試験は同一リージョンで「負荷生成VM／Pod → 本番相当LB／TLS → Gateway DP → 模擬上流」を用意し、生成・DP・上流・観測を必要に応じ別ノードに配置する。本番に近い体験は利用拠点から実経路のRTTや中継も再現し、別の結果として保存する。

KonnectのDPを検証する際は、対象DPと実際の入口を通す。CPの設定投入やプロビジョニングはDPプロキシ容量と独立した試験として扱う。

生成機を先に校正する

PoCの出発点の例は専用Linux VM 1台（4 vCPU／8 GiB）で、低負荷から上げる。速い模擬上流と実際のスクリプトで安全な上限を測り、CPU・RSS・NIC・FD・送信元ポート・NATを監視。生成機を増やして同じ総負荷を再試行し、結果が大きく変わる場合は負荷側の制約を切り分ける。

分散時は実測した1台の持続能力（RPS・接続・TLS確立/秒・帯域）で各必要台数を見積もり、最大値を採用。例として1台2,500 RPSに対し目標8,000 RPSならRPS軸は切り上げで4台。割当の偏りと予備容量を確認する。p99は全体の分布から求める。

結果を合格にする条件

  1. 入力を保存する。 目標RPSと接続条件、ルート・認証の構成、Gateway／plugin／ツールの版、vCPUとメモリ、LBとTLS終端、DPレプリカ、試験時間、シナリオと配布データの版を揃える。
  2. 事前にSLOを設定する。 例として「1,000 RPSの定常区間、実送信率99%以上、unexpected error 0.1%未満、p95 < 100 ms、p99 < 250 ms、未起動反復0」。シナリオ別に設定し、意図した429と意図しない429、タイムアウト、5xxを分ける。
  3. 計測点を合わせる。 クライアントの接続／TLS／応答、LBとDPの接続／エラー、上流の遅延、Gateway・IdP・Redis・観測パイプラインのCPU／メモリ／キューを見る。クライアント経過時間の評価には接続や待ちも含め、http_req_duration と接続指標も併記する。
  4. ウォームアップと反復実測を行う。 定常区間とコールドスタート、障害注入区間を分ける。同条件で原則3回程度から始め、区間値・ばらつきと最初の飽和点を保存する。容量値は目標SLOを継続して満たした最高段階として返す。
