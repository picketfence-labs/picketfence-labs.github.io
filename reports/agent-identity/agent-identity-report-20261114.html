01

最初に押さえること

結論

公開情報と実測に基づく

AIエージェントに「誰として」「何を」させるかを決める仕組みは、1つの製品では完結しません。Auth0はtokenを発行するIdP・認可サーバー、Kong AI Gatewayはエージェントの通信経路に立つ強制点です。役割が違うので、基本は置き換えではなく組み合わせです。次の数値は、実機で測ったものです。

役割分担利用者のログイン、同意、人の承認（CIBA）、委任tokenの発行はAuth0が担います。MCP toolの許可、第三者credentialの注入、通信の停止と記録はKongが担います。
Kongの強みエージェントに第三者のtokenを渡さずに使わせることと、IdPを変えずにMCP toolの認可をGatewayで一括して強制することです。どちらも今日の公開機能で動くことを確かめました。
止める速さ発行済みのaccess tokenは、IdPでは取り消せない場合があります。Kongの強制点で外せば数秒で止まります。IdPとKongの両方に停止手順を用意するのが安全です。
02

同じ層の製品ではない

役割の違い

エージェントの通信と、各製品の担当

今回検証した構成

矢印はリクエストの流れ。Kong AI GatewayはAuth0のtokenを検証して通し、必要なときだけToken Vaultから第三者credentialを取り出してupstreamへ付けます。エージェントとMCP clientには第三者のtokenは渡りません。

Auth0の担当

誰として動くかを決める

利用者のログイン、同意、エージェントへのtoken発行、利用者に代わるtoken交換（OBO、委任の連鎖をactで保持）、高リスク操作の前の非同期承認（CIBA）です。tokenを受けた側での強制は、アプリやMCP serverが実装します。

Kongの担当

通信経路で何を許すかを強制する

MCP・API・LLMへの通信を1か所で通し、tokenを検証してtool単位で許可・拒否します。第三者のcredentialはGatewayが付けるので、エージェントは持ちません。止めるときもGatewayの設定で済みます。Kong Identityは利用者がログインするIdPの代わりではなく、Gateway側の台帳とcredentialの保管庫です。

03

公開Docsだけでは言い切れない点を実機で確認

実測結果

Kong AI Gateway 2.3.1 · Auth0 Free

検証は4つです。Konnect上の検証用組織と、ローカルのhybrid data plane（Kong AI Gateway 2.3.1）、Auth0のFree tenant、簡易MCP serverで行いました。結果は検証時点の環境のもので、他の版や構成で同じになるとは限りません。

4つの検証と主な結果
検証問い結果判定
A. Kong Identityだけで自律エージェントIdPを持たないエージェントに、Kong IdentityがM2Mのtokenを発行し、Kong AI GatewayがMCP toolをエージェント単位で制御できるか成立。client credentialsで発行したtokenで、tool一覧の絞り込みと403拒否ができた（claim→Consumer Group、client ID、CELの3方式）。拒否された呼び出しはupstreamに届かない。MCP clientはProtected Resource Metadata（RFC 9728）から認可サーバーを見つけられた成立
A'. Principal台帳で認可Kong IdentityのPrincipal属性だけで、エージェント単位にtoolを許可できるか成立。CELでprincipal.metadataを判定。ただし属性変更や無効化の反映はPrincipalのcache（600秒）のため最大10分成立 反映に時間
B. Auth0のtokenでKongがtool認可Auth0が発行したエージェントのtoken（client credentials）で、KongがMCP toolをエージェント単位に制御できるか成立。claim（Auth0 Actionで付与）、client ID（sub）、scopeの各方式で許可・拒否できた。scope方式の403にはinsufficient_scopeが付き、不足しているscopeが分かる成立
B'. 止める速さAuth0側で止めたとき、発行済みtokenはKong経由でいつまで通るか。Kong側で止めるとどうかAuth0でgrant削除・secret変更・client削除をすると新規発行は1秒以内に止まるが、発行済みtokenは寿命（600秒）まで通った。Auth0にはaccess tokenのintrospectionが無い。Kong側でtool許可から外すと5.4〜6.9秒で403Kong側で数秒
C. Token VaultでGitHubを代理利用Auth0でログインした利用者に代わり、エージェントがMCP経由でGitHubを使えるか。エージェント側にGitHubのtokenが出ないか成立。利用者がGitHubを一度承認すると、以後はKongが利用者のGitHub tokenをupstreamへ付けた。エージェント・MCP clientへの応答とログに、GitHubのtokenは0件成立
C'. Token Vaultの停止providerを無効にすると、どれだけで止まるか約282秒後に止まった（Gatewayのcredential cache 300秒）。止まった応答はHTTP 500。有効に戻すと約2秒で復帰即時ではない
観測した事実

未接続のときの振る舞い

利用者がまだGitHubを接続していないと、エージェントに見えるtoolは接続を案内する2つだけでした（token_vault_authenticateとtoken_vault_check_authentication_status）。本物のtoolは隠れていて、呼ぶとnot foundになります。案内のtoolは、10分有効の認可URLを返します。

解釈と限界

停止は二段で設計する

IdP側の停止は新しいtokenを止めますが、発行済みのaccess tokenはJWTの署名検証だけで通り続けます。Kong側のtool許可からの除外は数秒で効きました。Token Vaultのprovider停止は約5分、Principal台帳での停止は最大10分かかります。用途ごとに、どこで止めるかを決めておく必要があります。

要求別の比較

MCPAuth for MCP（GA）：MCP serverの保護、CIMD手動登録、OBO。Dynamic CIMDはEAMCPの集約・tool ACL・credential注入。MCP 2025-11-25と2026-07-28（stateless）に対応（実測）MCPの認可サーバー＝Auth0、MCPのgateway＝Kongの分担が自然

エージェント自身の認証方式client secret。private_key_jwtとmTLSはEnterprise plan（mTLSは追加のadd-onも必要）Kong Identityは検証時点でclient secretのみ利用できた標準が勧める非対称鍵の認証は、Auth0はEnterpriseで提供、Kongは未提供
運用形態SaaS。SDK多数（LangChain、Vercel AI等）。アプリに組み込む型Konnect＋data plane（hybrid可）。エージェント側の変更はGateway経由にすることが中心組み込み型か経路型か。data residencyは個別に確認

一致する要求はありません。

05

条件で決める

構成の選び方

基本形：Auth0とKongの組み合わせ

検証B・Cで動作を確認

順番担当何をするか
1Auth0（または既存のIdP）利用者をログインさせ、エージェントへaccess tokenを発行する。高リスク操作はCIBAで利用者の承認を取る
2Kong AI GatewayエージェントからのMCP・API・LLMへの通信を受け、Auth0のtokenを検証し、tool単位に許可・拒否する。scopeで許可するのが最も素直
3Kong Token VaultMCP経路で第三者SaaSを使うときは、Auth0を信頼するIdPに指定し、利用者ごとのcredentialをGatewayで注入する。エージェントにtokenを渡さない
4両方停止手順を二段で用意する。IdPで新規発行を止め、Kongで発行済みtokenの通行を止める

エージェントが第三者SaaSのSDKを直接使う構成ならAuth0 Token Vault、MCPやAPIの経路を通す構成ならKong Token Vaultを選び、同じ接続を両方に登録しないようにします。

Kongが合う条件

経路で統制したい

利用者認証のIdPは決まっていて変えたくない。エージェントからMCP server・社内API・LLMへの通信を1か所で強制し、記録したい。GitHub・Slack・Google等のcredentialをエージェントやMCP clientに持たせたくない。MCP toolの利用可否をIdPのgroupやscopeでまとめて制御したい。すでにKong GatewayやKonnectを使っている。

Kongだけでは足りない条件

他の製品やアプリで補う

利用者のログインやCIAMそのもの（→Auth0等のIdP）。高リスク操作の前の人の承認（→Auth0のCIBA）。RAGの文書単位やtool引数単位の認可（→FGAやアプリ）。Token Vaultを完全オンプレミスや閉域で動かす（→現状不可、Konnect必須）。B2B SaaSで顧客組織ごとにエージェント連携を提供する（→Auth0のOrganizationsとToken Vaultが先行）。

自律エージェント（利用者がいない）の場合

検証A

IdPを持たない自律エージェントなら、Kong IdentityのM2M用認可サーバー、Kong AI Gateway、Token Vaultで一式がKong内に収まり、tool単位の制御まで動きました。ただし、エージェント自身の認証は検証時点でclient secretだけでした。MCPの拡張仕様やIETFのdraft、主要IdPは静的なsecretを避け、private_key_jwt・mTLS・workload identityを勧めています。社内PoCや、短い寿命のtokenとsecretの定期的な入れ替えで運用できる用途に向きます。本番の標準準拠を求める場合は、提案前に提供状況を確認してください。

06

PoC・設計の前に

留意点

業界標準の現状

自律エージェントがtokenを得るのにclient credentials grantを使うのは、共通のパターンです（MCPの拡張「OAuth Client Credentials」はStable）。一方で、エージェントがclientとして自分を証明する方式は、静的なsecretから、非対称鍵（private_key_jwt）、mTLS、workload identityへ移っています。IETFのエージェント関連文書はまだdraft（例：draft-ietf-wimse-aims）で、「IETF標準」と言える段階ではありません。A2A Protocol v1はエージェントのidentityを規定せず、AgentCardで認証方式を示すだけです。主要IdPはエージェントを専用の主体として扱い始めています（Microsoft Entra Agent ID、Okta for AI AgentsはGA、Auth0 Agent as PrincipalはEA）。

設計時の注意（実測で分かったこと）
項目内容
1つのMCP serverの認証設定MCP serverに付けられる認証設定は1つだけでした。1つの設定に複数のissuerを許可すれば2つのIdPのtokenを通せますが、MCP clientへ案内される認可サーバーは1つになり、group名も共有になります。IdPを混在させるなら経路を分けるのが安全です
scopeの判定scope方式では、scope文字列を空白で分割する指定（.scope | split(" ")）が必要でした
Token Vaultの設定形MCP serverにtoken_vaultとdatastoresを指定する形で動きました。復号用の秘密鍵は、Konnectには{vault://…}の参照としてのみ登録でき、実体はdata plane側に置きます
認可URLのホストToken Vaultの認可URLとcallbackは、data planeが受けたリクエストのホストとポートから作られます。前段にロードバランサーがある場合は、転送ヘッダーの扱いを先に決めてください
停止時の応答Token Vaultのproviderを止めたときの応答はHTTP 500でした。エージェント側で再接続の案内として扱えるかは未確認です
Auth0 tokenの寿命ログインから第三者SaaSの承認、tool呼び出しまでの間にtokenが切れないよう、APIのtoken寿命を設計してください（検証では600秒で一度失効）
拒否時の応答形式tool ACLで拒否されたときは、JSON-RPCのエラーではなくHTMLの403が返りました
07

数字と根拠の読み方

出典と定義

対象範囲
Auth0の「Secure AI Agents & MCP Servers」関連機能と、Kong AI Gateway・Kong Identity（Token Vault、Principal、Auth Server）。価格と契約条件は比較していません。将来の計画・roadmapは含めていません。

公開情報の出典
Auth0 Docs・changelog（2026/11/13確認。private_key_jwtのplan条件は「Application Credentials」で2026/11/14確認）。Kong Docs（developer.konghq.com、Token Vault・AI Gateway changelog 2.3.0（2026/11/04）ほか、2026/11/13確認）。MCP仕様と拡張、IETF draft、A2A Protocol v1.0.1。

実測の条件
Kong Konnect（us region）の検証用組織、Kong AI Gateway 2.3.1のhybrid data plane（ローカルDocker）、Auth0 Free tenant、Python製の簡易MCP server、GitHub OAuth App（read:userのみ）。2026/11/13〜11/14に実施。

実測と推論の区別
表中の「実測」は検証環境で観測した結果です。cacheの秒数など、理由の説明にはdata planeのソースを読んだ推論を含みます。Auth0のEA機能とEnterprise限定機能は実機で試していません。

未確認の事項
Auth0 Token Vaultとの同条件での比較、Token Vaultの利用者credential削除とSaaS側の許可取り消しの挙動、Konnectの監査ログへの記録、Kong AI Gateway 2.3.1以外の版での挙動。
